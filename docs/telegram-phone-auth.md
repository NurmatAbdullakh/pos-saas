# Telegram Gateway phone authentication

Phone sign-in uses the official Telegram Gateway API. Telegram delivers the verification code to the user's **Verification Codes** chat; the POS SaaS backend never reads Telegram chats and does not need a Telegram bot, BotFather token or webhook.

## Local environment

In `apps/api/.env`, set:

```env
TELEGRAM_GATEWAY_TOKEN=<your-gateway-api-token>
OTP_SECRET=<a-long-random-secret>
```

Keep real values private. Never commit the token.

In Telegram Gateway account settings, add your laptop's current public IPv4 address as a single-host CIDR (for example, `198.51.100.10/32`). If your ISP changes your public IP, update the allowlist. Do not use `0.0.0.0/0`.

## Database migration

From `apps/api`, run:

```bash
npm run migrate:up
```

The first migration adds phone-number support and phone OTP challenges. The follow-up migration adds the Gateway request ID and removes the obsolete bot-based account-linking tables.

## API flow

1. `POST /api/auth/phone/request-otp` with `{ "phoneNumber": "+998901234567" }`.
2. The backend calls Telegram Gateway `sendVerificationMessage` with the E.164 phone number and stores the returned `request_id`.
3. Telegram sends the code to the user's Verification Codes chat.
4. `POST /api/auth/phone/verify-otp` with `{ "challengeId": "...", "phoneNumber": "+998901234567", "code": "123456" }`.
5. The backend calls `checkVerificationStatus`. If Telegram returns `code_valid`, the API creates or finds the user and creates the existing refresh-token session.

Codes are generated by Telegram (six digits requested), expire after five minutes, and are checked by Telegram rather than stored in our database. The backend also limits requests to five per phone number in a rolling 15-minute window and limits local verification attempts.

## Testing

Telegram documents that messages sent to the phone number associated with your Gateway account are free for testing. Start by testing only with your own number. The phone number must be in E.164 format.

## Security notes

- Gateway calls are made only from the backend using the secret API token in the Authorization Bearer header.
- Never expose the Gateway token in frontend code or return it from an API.
- Keep the API token out of Git and logs.
- Before public launch, add IP-based rate limiting and monitoring in addition to the current per-phone limit.
- Users must voluntarily provide their phone number to receive Gateway verification messages.
